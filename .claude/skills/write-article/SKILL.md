# 記事執筆ルール

study_design_pattern リポジトリで `学習内容/chapterXX_パターン名.md` を新規執筆・修正・校正する際に適用する。

## 生成範囲

Claude は記事全体（導入・シナリオ・既存コードの仕様・好ましくない実装・正しい実装・まとめ・深堀り）のたたき台を執筆する。ユーザーはその後、自分の言葉での加筆修正を行う。

構成変更や文章追加を提案する際は、必ず複数案を提示し、承認を得てから実装する。

## シナリオ方針

書籍コードの丸パクリを避け、各章で独自の業務シナリオを新たに考案する。シナリオは引用ブロックに記載する。

## 出力先

- `学習内容/chapterXX_パターン名.md` に直接書き出す
- コミットや別途設計ドキュメントの作成は不要

## 記事の構成順序

1. 既存コード（シナリオ提示）
2. 追加要件（問題提起）
3. 好ましくない実装（アンチパターン）
4. パターンを使った正しい実装（パターン適用後のメリットをここで自然に示せる場合は、このセクション内で言及する）
5. メリット（4. で十分に触れられた場合は省略可）
6. まとめ
7. 深堀り（GoF 分類を含む複数のサブセクション）

セクション間の流れが断絶しないよう、起承転結を意識して構成する。本文の流れを壊す補足は、流れが切れない位置に移動するか、末尾の深堀りセクションに統合する。

## 記事の題名フォーマット

```
# 英語（カタカナ）パターン ― 説明
```

例: `# Iterator（イテレータ）パターン ― コレクションの走査を統一する`

## 冒頭文の構成

「問題提起 → シナリオ → 解決するのがパターン」の順で構成する（chapter04・chapter05・chapter07・chapter08で確立）。

1. **問いかけ＋あるある例**（問題提起）：「次のような経験をしたことはありませんか？」に続けて、blockquote で読者が経験しうる具体的な場面を補足する
2. **記事の内容紹介**：「この記事では、（シナリオ）を通して、（パターン名）パターンがこの問題をどのように解決するかを紹介します。」の形で、シナリオ→パターンによる解決の順に記事の内容を予告する

※ chapter01 のように記事冒頭でシナリオ名をまだ提示できない場合は、2文目を「この記事では、そうした『（問題の本質を表すフレーズ）』の悪い例と、それを解決する『（パターン名）パターン』を、具体例を通して紹介します。」とする

パターン名・パターンの役割・「そのための設計が〜です」のような解決の言及は、シナリオに触れる前の文に書かない。解決とパターン名は、2文目（シナリオの直後）でまとめて初出させる。

実務感覚への共感や問題の本質を補足する文（chapter02を参照）を1文目と2文目の間に追加してもよい。追加する場合も、その文中でパターン名や解決を先出ししない。

冒頭の問いかけ（blockquote）は、記事のシナリオに固有のドメイン語や実装詳細を直接書かず、抽象度の高い表現にとどめる。読者が自分の経験に重ねやすいよう、具体的な型名・メソッド名・演算子名は入れない。

## 目次

冒頭の導入文の直後に `## 目次` を必ず追加する。

目次内に同名の見出しが複数存在する場合は、重複する見出しの直前に `<a id="一意のid"></a>` を挿入し、目次のリンクはその id を参照する形式にする（自動生成の `-1` サフィックスは使用しない）。

## 記事冒頭のあるある例

冒頭の「あるある」引用ブロックには、本記事のシナリオとは独立した、一般的な業務上の経験を書く。シナリオ特有の固有名詞（テストデータ、注文など）は含めない。パターンの本質（「手順が多い・種類が増える・重複が膨らむ」等）を一般的に表す内容にする。

## 好ましくない実装の直前に挿入する定型注記

```
※ここで一旦読むのを止めて、ご自身でコーディングを行なってみてください。その後で、続きを読んでください。
```

（chapter02 以降で統一。chapter01 のみ blockquote 形式を使用）

## 問題点提示前の転換文

好ましくない実装の実行結果が一見すると正常（目に見える不具合がない）な場合、問題点の箇条書きに入る直前に以下の定型文を挿入する。

```
コンパイルエラーがなく結果が出力されていることから、一見すると実装・動作確認ともに問題ないように見えます。

しかし、この実装には以下の問題点があります。
```

（chapter04・chapter09 で確立。「一見すると〜ように見えます」という留保を挟むことで、直後の「しかし」との論理的な接続を自然にする）

実行結果自体に目に見える不具合がある場合（chapter07・chapter08 のように、出力結果を見比べると矛盾が発覚するパターン）は、この定型文を使わず、その不具合を具体的に指摘する文章に差し替える。

## 深堀りセクション

深堀りは本文とは独立したセクションとして末尾にまとめる。各深堀りセクションは `<a id="深堀りN"></a>` の HTML アンカータグをセクション直前に置く（`①`などの囲み数字はGitHubのアンカー生成で除去されるため、明示的に id を設定する必要がある）。

```
<a id="深堀り1"></a>

## 【深堀り①】タイトル
```

目次のリンクは `#深堀りN`（数字のみ）で参照する。

```
- [【深堀り①】タイトル](#深堀り1)
```

### GoF 深堀りの定型文

GoF セクションは深堀りの最後のサブセクションに配置する。番号は章によって異なる。

**見出し（番号以外固定）：**

```
## 【深堀りN】GoF デザインパターンとの位置づけ
```

**本文テンプレート：**

```
今回使った ○○ パターンは、GoF（Gang of Four）の 23 のデザインパターンのうち「生成パターン」に分類されます。<br>
詳しくは「GoF」で検索してみてください。
```

カテゴリ（生成・構造・振る舞いパターン）はパターンによって異なるので、対象パターンに応じて差し替える。

## まとめと深堀りの境界文

まとめセクションの末尾（`---` の直前）に必ず以下の2行を挿入する。

```
本記事の内容はここまでとなります。

以降は「もう少し深く知りたい」という方向けの補足となります。今回学んだパターンに繋がる設計原則や、実務で役立つ背景知識について触れています。
```

## まとめセクションの書き方

「## まとめ」は2〜3文の文章のみで構成する。表・箇条書きは使わない。`<br>` で段落内の改行を入れて読みやすくする（chapter04・chapter05が手本）。複数の観点を羅列している場合は削る。

## 校正時の指摘提示方針

校正を依頼された場合は、「これ以上指摘事項がない」と確認できるまで全体をチェックしてから、まとめて指摘事項を提示する。都度出しは不可。

## 「〇〇を見て分かるように」系の表現

「実装を見て分かるように」「上記を見て分かるように」のような、読者に判断を委ねる表現は使用しない。何が問題なのか・何が変わったのかを文章で具体的に記述する（コードコメントで示せる場合はそちらでもよい）。既存記事にこの表現が見つかった場合は、詳細化の修正を提案する。可能であれば事前に修正案を提示して反映する。

## 文体

記事全体を「です・ます調」に統一する（Qiitaの主流スタイル）。コードブロック・表・見出しは対象外。

## コードブロックのファイル名表記

コードブロック直前に太字インラインコードでファイル名を記載する。`:filename` 形式（Zenn/Qiita拡張）は使用しない。太字ファイル名ラベルと直後の ```` ```java ```` フェンスの間には、必ず空白行を1行入れる。

**`Fruit.java`**

```java
public class Fruit { ... }
```

ソースコードの引用や補足コードが本文の流れを断ち切る場合は、深堀りセクションへ移動する。

## Main クラスの参照表記

- コードブロックラベル: `**`Main.java`**`
- 本文中でクラスを指す場合: `` `Main` ``（`` `Main.java` `` は使わない）
- 「既存コードの仕様」セクションのクラス一覧のみ例外: `` `Main`（実行クラス） ``（他のクラス記述と形式を統一するため）
- 「実行クラス」は概念として述べる文脈では使用可

## 既存コードの仕様での既存クラスの提示形式

- 既存クラス: `- \`ClassName\`（既存クラス）` の箇条書き＋説明文＋フィールド表/メソッド表＋コードブロックの形式に揃える。コード内に説明コメント（`// 顧客情報` 等）は書かず、説明は表側に記載する
- パターン適用で新規作成するクラス（`TestData`/`TestDataBuilder` など）は `**`Class.java`**` ＋コードブロックのみで、箇条書き・表は不要
- 2つ目以降のクラスの箇条書き（`- \`ClassName\`（既存クラス）` 行）の直前に `<br>` を挿入し、前のクラスのコードブロックとの間に視覚的な区切りを設ける（先頭のクラスには不要）

既存クラスを書く/直す前に、過去章の同セクションを grep して既存クラスの提示形式を確認する。

## パッケージ宣言

クラスを示す Java コードブロックの先頭には `package example;` を記載する（デフォルトパッケージを避け、パッケージを明示する）。

例外:

- 記事内で実際にパッケージ構成を扱う場合（例: chapter04の `framework`、`visitorcard`、`employeecard` など）は、`example` パッケージのサブパッケージとして配置する（`example.framework`、`example.visitorcard`、`example.employeecard` など）
- JDK のソースコードを引用する場合（例: `java.lang.String` や `java.lang.Object` など）は、実際の `package java.lang;` を使用する
- クラス全体ではなく式・差分のみを示すスニペットには付けない

## 実務のディレクトリ構成との差異に関する注釈

記事では簡潔さのため `package example;` 直下にクラスをフラットに配置しているが、実務では別ディレクトリ（パッケージ）に切り出すのが一般的なクラス（エンティティなど）が初出する箇所では、その旨を短く注釈する。読者が記事のフラットな構成を実務上の正解と誤解しないようにするための措置。

その章のクラス総数が少なくても省略しない。最小構成の入門記事ほど読者がそのまま模倣しやすいため、クラス数を問わず注釈を入れる。

## 処理内容の簡略化に関する注釈

記事では外部システム（DB・API・SMTP サーバーなど）との実際の連携処理を行わず、コンソールへの出力で代替している。この簡略化を行っている箇所がシナリオ内で初出する際、その旨を短く注釈する。

- 挿入位置: シナリオ引用ブロックの直後、次の見出し（多くは「既存コードの仕様」）の直前
- 文言テンプレート: `※実際の（処理内容）では（実際に必要な連携）を行う実装が必要ですが、本記事では ○○ パターンの解説に集中するため、コンソールへの文字列出力のみとします。`

## JDK ソースコードの引用

JDK（OpenJDK）のソースコードを記事に掲載する場合は、必ず引用元を明記する（OracleのGPL v2 with Classpath Exceptionライセンスが適用されるため）。コードブロックの直下に `> 引用元: OpenJDK [ファイル名](GitHub URL)` の形式で記載する。対象となりやすい例: `Iterable.java`、`Iterator.java`、`ArrayList.java` など。

## 参照スタイル

基本は `（→ [セクション名](#anchor)）` のインライン参照方式を使う。読者の視線が途切れず、環境依存もなく、学習記事としての流れに合う。

新規記事・既存記事の修正ともにインライン参照をデフォルトとする。ただし、コードブロック内など**インラインリンクを置けない場所**では脚注方式（`[^1]`）を採用してよい。脚注方式を選ぶ際は「インラインに置けない理由」が明確であることを確認する。

脚注をインライン参照に変換する際、脚注本文（解説の全文）を本文中に展開しない。脚注本文が深堀りセクションの要約に過ぎない場合、本文側は「※◯◯に関する説明（→ [見出し](#anchor)）」のような短いポインタのまま保ち、詳細は深堀り側に委ねる。インライン化はリンク記法の問題を解決するだけで、説明量を増やす理由にはならない。

## ポストプロセススクリプト

記事が完成した後、以下の順で実行する。

```bash
# 1. インラインコード前後の日本語との間にスペースを挿入
python3 bin/fix_backtick_spaces.py 学習内容/chapterXX_xxx.md

# 2. 英字と日本語の間にスペースを挿入（実行後、目視で不要スペースを削除してフィードバックをもらう）
python3 bin/fix_english_japanese_spacing.py 学習内容/chapterXX_xxx.md
```
