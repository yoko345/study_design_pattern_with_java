以下は本文から削除した完成稿（`Semaphore` 版）。将来、並行処理をテーマにした発展記事などで再利用できる可能性があるため保存する。

**`Semaphore.java`（一部抜粋）**

```java
public class Semaphore implements java.io.Serializable {
    private final Sync sync;

    public Semaphore(int permits) {
        sync = new NonfairSync(permits);
    }

    public void acquire() throws InterruptedException {
        sync.acquireSharedInterruptibly(1);
    }

    public void release() {
        sync.releaseShared(1);
    }
}
```

> 引用元: OpenJDK [Semaphore.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/util/concurrent/Semaphore.java)

`acquire` メソッドと `release` メソッドの中身を振り返ると、許可証（permit）の管理と待機スレッドの調整は、`Semaphore` クラスが内部に持つ `sync` フィールドに委ねられています。ただし、`acquire` を呼び出す側のスレッド（本記事の `Colleague` インターフェースの実装に相当）が直接やり取りする相手はあくまで `Semaphore` クラスであり、`sync` はその内部実装の詳細です。スレッドは、他のスレッドが何個の許可証を保持しているか、他に誰が `acquire` で待機しているかを一切知る必要がなく、その調整はすべて `Semaphore` クラス（本記事の `RobotManager` に相当する調整役）に集約されています（`sync` は `AbstractQueuedSynchronizer` を継承した内部クラスで、待機スレッドのキューイングなど複雑な同期処理を行いますが、本記事では割愛します）。

本記事の `TransportRobot` クラスが `RobotManager` クラスに進入を要求するだけでレーンの空き状況の判定を一切持たなかったのと同様に、`Semaphore` を使うスレッドも、許可証（permit）の残数、つまり同時にアクセスできる上限をもとにした可否判定を一切持たず、その調整はすべて `Semaphore` クラスに集約されています。

## 新規記事候補：Composite × Iterator（木構造の走査を分離する）

chapter11_Composite.md の深堀り③として執筆したが、Composite パターンの主軸から逸脱し、実質的に Iterator パターンをゼロから教える内容になってしまうため本文からは削除。内容自体の完成度は高いため、将来 Composite と Iterator を組み合わせた発展的な単独記事として出す候補として保存する。

### 追加要件からの導入

本記事の `printTaskList` メソッドを振り返ると、`TaskGroup` クラス自身が子を再帰的にたどりながら、最後の個別要素（`Task`）で出力処理行っています。<br>
ここで、「見積工数が 20 時間を超える要素だけを抽出して警告を出力する」という追加要件が発生したとしましょう。

本記事の抽象クラス `TaskComponent` には、木構造をたどるロジックと出力処理が一体化した `printTaskList` メソッドしか用意されていません。そのため、追加要件は `TaskGroup` クラスに専用メソッドを追加する実装となります。

**`TaskGroup.java`**

```java
package example;

public class TaskGroup extends TaskComponent {
    // 他のフィールドは省略

    protected void printOverEstimatedTasks(String prefix, int threshold) {
        if (getEstimatedHours() > threshold) {
            System.out.println("警告：" + prefix + name);
        }
        for (TaskComponent child: children) {
            if (child instanceof TaskGroup) {
                ((TaskGroup) child).printOverEstimatedTasks(prefix + name + " / ", threshold);
            } else if (child.getEstimatedHours() > threshold) {
                System.out.println("警告：" + prefix + name + " / " + child.getName());
            }
        }
    }
}
```

**`Main.java`**

```java
package example;

public class Main {
    public static void main(String[] args) {
        // 他の処理は省略

        implGroup.printOverEstimatedTasks("", 20);
    }
}
```

**実行結果**

```
警告：実装
警告：実装 / API実装
警告：実装 / テスト
```

このように、行いたい処理の種類が増えるたびに `TaskGroup` クラス自身へメソッドを追加することになり、「木構造をたどるロジック」と「取り出した要素に対する処理内容」がお互いに依存した状態になってしまいます。さらに、個別要素と複合要素を区別する `instanceof` も必要になり、Composite パターンが本来解決したはずの「個別要素と複合要素を同一視する」という利点も薄れてしまいます。

この問題点を解決するのが **Iterator パターン**です。<br>
木構造を「1 つずつ順番に取り出せる集合」として扱うクラスを用意し、たどるロジックをその中に閉じ込めることで、呼び出し側はたどり方を意識せず、取り出した要素に対する処理だけを自由に書けるようになります。

### Iterator パターンによる解決（スタックを使った遅延走査版）

まず、`TaskGroup` クラスに `Iterable<TaskComponent>` を実装させ、木構造を先頭から順にたどる `Iterator` の実装クラスを用意します。

**`TaskComponentIterator.java`**

```java
package example;

public class TaskComponentIterator implements Iterator<TaskComponent> {
    private Deque<TaskComponent> stack = new ArrayDeque<>();

    public TaskComponentIterator(TaskGroup root) {
        stack.push(root);
    }

    @Override
    public boolean hasNext() {
        return !stack.isEmpty();
    }

    @Override
    public TaskComponent next() {
        if (!hasNext()) {
            throw new NoSuchElementException();
        }

        TaskComponent current = stack.pop();
        if (current instanceof TaskGroup) {
            List<TaskComponent> children = ((TaskGroup) current).getChildren();
            for (int i = children.size() - 1; i >= 0; i--) {
                stack.push(children.get(i));
            }
        }
        return current;
    }
}
```

`TaskGroup` クラス側に必要な変更は、クラス宣言へ `implements Iterable<TaskComponent>` を追加した上で、`children` フィールドを取得する `getChildren` メソッドと、`TaskComponentIterator` を生成する `iterator` メソッドを追加するだけです。

```java
public List<TaskComponent> getChildren() {
    return children;
}

@Override
public Iterator<TaskComponent> iterator() {
    return new TaskComponentIterator(this);
}
```

これにより、呼び出し側は木構造のたどり方を一切意識せず、取り出した要素に対する処理だけを自由に書けるようになります。

```java
for (TaskComponent component: implGroup) {
    if (component.getEstimatedHours() > 20) {
        System.out.println("警告：" + component.getName());
    }
}
```

**実行結果**

```
警告：実装
警告：API実装
警告：テスト
```

`component` には `implGroup` 自身（複合要素）と、その配下の `Task`（個別要素）が順番に渡ってきますが、どちらも同じ `TaskComponent` 型として扱われるため、しきい値判定のコードを型ごとに分ける必要はありません。ここでも、Composite パターンによる「個別要素と複合要素の同一視」の効果が生きています。<br>
`TaskGroup` クラス自身やその内部の再帰処理には一切手を加えず、呼び出し側のループの中身を書き換えるだけで任意の処理を追加できるようになった点が、Iterator パターンによる解決です。木構造をたどるロジックを `Iterator` の実装クラスに閉じ込め、取り出した要素に対する処理を呼び出し側に委ねることで、両者の責務を分離できるという点が、Iterator パターンと Composite パターンの関係になります。

### 別解：既存の再帰処理を流用した簡易版（分量を抑えたい場合）

`TaskComponentIterator` のコンストラクタで一気に木構造をたどって `List` に集約し、あとはインデックスを進めるだけにする書き方もある。スタック不要でシンプルだが、木構造全体を先に走査し終える点がスタック版（遅延走査）と異なる。

```java
package example;

public class TaskComponentIterator implements Iterator<TaskComponent> {
    private List<TaskComponent> elements = new ArrayList<>();
    private int index = 0;

    public TaskComponentIterator(TaskGroup root) {
        collect(root);
    }

    private void collect(TaskComponent component) {
        elements.add(component);
        if (component instanceof TaskGroup) {
            for (TaskComponent child: ((TaskGroup) component).getChildren()) {
                collect(child);
            }
        }
    }

    @Override
    public boolean hasNext() {
        return index < elements.size();
    }

    @Override
    public TaskComponent next() {
        TaskComponent component = elements.get(index);
        index++;
        return component;
    }
}
```

## chapter10で追加予定（State パターンの章公開後）

### 【深堀り】State パターンとの違い

本記事の `RouteNavigator` クラスを振り返ると、`RouteSearchStrategy` 型のフィールドに処理を委譲する構造をしており、これは「**State パターン**」の構造とよく似ています。どちらも、切り替え可能なオブジェクトへの委譲によって処理内容を変える点は共通しています。

両者の違いは、状態（または戦略）を誰が切り替えるかにあります。<br>
Strategy パターンでは、利用する側（本記事の `Main` クラス）が、目的に応じたアルゴリズムを選んでコンストラクタに渡します。切り替え後に、内部の状態が自律的に別のアルゴリズムへ遷移することはありません。<br>
一方、State パターンでは、具体的な状態クラス自身が「次はどの状態に遷移するか」を判断し、内部で状態を切り替えていきます。例えば、注文状態が「注文済み → 発送済み → 配達完了」と遷移していくように、状態同士が連鎖的に自分自身を置き換えていく点が特徴です。

つまり、Strategy パターンは「外部から選んだアルゴリズムを実行時に固定する」ことが目的であるのに対し、State パターンは「オブジェクト自身が状態遷移のルールを持ち、状態に応じて振る舞いを変える」ことが目的である、という違いがあります。

## chapter10で追加予定（Flyweight パターンの章公開後）

### 【深堀り】Flyweight パターンとの関係

本記事の `ShortestDistanceStrategy`・`ShortestTimeStrategy`・`BalancedStrategy` クラスを振り返ると、いずれもフィールドを持たない無状態（ステートレス）なクラスです。これは、「**Flyweight パターン**」が対象とする構造と相性が良い特徴です。

Flyweight パターンは、複数の箇所で使い回しても問題のないオブジェクトを共有し、生成コストやメモリ消費を抑えるパターンです。本記事の `RouteSearchStrategy` の実装クラスは内部状態を持たないため、複数の `RouteNavigator` インスタンス間で同じ `ShortestDistanceStrategy` のインスタンスを安全に共有でき、利用するたびに `new` する必要がありません。

つまり、Strategy パターンで実装したアルゴリズムがステートレスである場合、そのインスタンスを Flyweight として共有することで、Strategy パターンと Flyweight パターンを組み合わせて使うことができます。

## chapter13で追加予定（Visitor パターンの章）

### 【深堀り】ポリモーフィズムとは何か、なぜ二重ディスパッチの2段目はポリモーフィズムと呼ばないのか

本記事の【深堀り①】二重ディスパッチの仕組みでは、1段目（実行時の型によるディスパッチ）を「通常のメソッドオーバーライドによるポリモーフィズム」と説明する一方、2段目（静的な型によるディスパッチ）ではポリモーフィズムという語をあえて使っていない。この使い分けの根拠を、ポリモーフィズムの定義から掘り下げる内容。

ポリモーフィズム（多態性）とは、同じ呼び出し方（同じメソッド名・シグネチャの呼び出し）でも、呼び出す対象（オブジェクト）によって実際に実行される処理が異なるという性質のこと。Java では次の仕組みを指す。

- 親クラス（またはインターフェース）型の変数に、子クラスのインスタンスを代入できる
- その変数に対してメソッドを呼び出すと、変数の宣言上の型ではなく、実際に代入されているオブジェクトの実行時の型に応じたメソッド（オーバーライドされたもの）が呼ばれる
- どのメソッドが呼ばれるかは実行時に決まる（＝動的束縛）

本記事の `TaskComponent` 型の変数 `child` に `Task` のインスタンスが入っていても `TaskGroup` のインスタンスが入っていても、`child.accept(visitor)` という同じコードで、実行時の型に応じてそれぞれの `accept` が呼ばれる（二重ディスパッチの1段目）——これがポリモーフィズムである。

対して、二重ディスパッチの2段目（`visitor.visit(this)` のオーバーロード解決）は、コンパイル時に確定した `this` の型によって呼び出すメソッドが決まる仕組み（静的束縛）であり、「実行時に決まる」というポリモーフィズムの定義には当てはまらない。この違いを踏まえ、2段目の説明にポリモーフィズムという語を使うと、1段目で説明した動的束縛との区別が崩れて読者を混乱させるため、あえて触れていない。

## chapter16で追加予定（Observer パターンの章公開後）

### 【深堀り】Observer パターンとの違い

Mediator パターンは、「複数のオブジェクトの間で状態の変化を伝え合う」という点で Observer パターンと似ており、しばしば混同されます。両者を分けるのは、状態の変化を伝えた後、誰が判断を行うかという役割分担です。

Observer パターンは、Subject（状態を持つ側のオブジェクト）が Observer に対して「状態が変わったこと」を一律に通知するだけで、通知を受け取った後の判断はすべて Observer 自身に委ねられます。Subject は、通知先の Observer 同士の関係や、通知を受けてどう振る舞うべきかについては関知しません。<br>
一方 Mediator パターンでは、`RobotManager` クラスの `requestEnterLane` メソッドのように、仲介役自身が `TransportRobot` クラスから受け取った情報をもとに判断を行い、`onLaneGranted` メソッドや `onLaneDenied` メソッドで個々の `TransportRobot` クラスに対して異なる結果を返します。

つまり、`TransportRobot` クラス同士の関係を調整する「判断のロジック」そのものを `RobotManager` クラスが担っている点が、Observer パターンとの大きな違いです。

### chapter02（Adapter）

**追加候補：DIP（依存性逆転の原則）**

- 対応箇所：`Main` クラスの変数宣言（好ましくない実装② vs 正しい実装①）、`PaymentProcessor` インタフェース、`SamplePayAdapter`
- 根拠：好ましくない実装②では `SamplePayClient samplePay = new SamplePayClient();` のように、呼び出し元 `Main` が具体クラス `SamplePayClient` の型で変数を宣言しており、具体クラスへの直接依存が発生している。正しい実装①では `PaymentProcessor samplePay = new SamplePayAdapter();` のように、共通インタフェース `PaymentProcessor`（抽象）に依存する形へ変わっており、これはDIPの教科書的な適用例になっている。
- 非重複性：既存の【深堀り②】OCPは「`CreditCardPayment`・`SamplePayClient` を変更せず `SamplePayAdapter` を追加するだけで拡張できる」という“修正不要”の側面だけを説明しており、`Main` 側の変数宣言が抽象型に変わったという“依存の向き”の話には触れていない。chapter04（Factory Method）でDIPとOCPを別々の深堀りとして両立させている前例があるので、同じ構成をchapter02にも当てはめられる。
- 見送った原則：SRP（`SamplePayAdapter` はもとから「適合」という単一の役割しか持たず、Before状態でも責務混在が起きていないため持ち出す理由がない）、LSP・ISP（継承版Adapterや `PaymentProcessor` インタフェースのどちらにも、置換や過剰メソッドの論点が具体的なコードとして現れず、こじつけ感が出る）。

### chapter05（Singleton）

**追加候補：DIP（依存性逆転の原則）― ただし「実現例」ではなく「トレードオフ・注意点」としての深堀り**

- 対応箇所：`OrderService.placeOrder`、`PaymentService.processPayment`、`Logger.getInstance()`
- 根拠：正しい実装の `OrderService`・`PaymentService` はどちらも `Logger.getInstance().log(...)` という形で、インタフェースを介さず `Logger` という具体クラスに直接依存している。他章のDIP/OCP深堀りは「抽象に依存させることで拡張・差し替えを容易にする」という良い側面を説明しているが、本件はその逆で、Singletonパターンの弱点（`Logger` を使う側がテスト時にモックへ差し替えづらい、利用クラス全てが具体クラスに縛られる）を示す好例になっている。
- 非重複性：chapter05は現時点で原則系の深堀りが1つもない（既存の深堀りは①privateコンストラクタが必要な理由・②スレッドセーフ化・③n個への制限・④enumによるSingleton・⑤GoF位置づけの5本のみ）、完全に手つかずの領域。
- 書き方の注意：他章のDIP/OCP深堀りは「パターンがこの原則を実現する手段である」という肯定的な書き方で統一されているが、本件は逆に「Singletonパターンを使うとDIPに反する依存が生まれやすい」という注意喚起の書き方になる点に注意。書く場合は「ではどうするか」（例：`Logger` をインタフェース化してDIする、Singletonへの依存を最小限のラッパー越しにする、など）に軽く触れると実務的な締めになる。
- 見送った原則：SRP（`Logger` 自体はすでに単一責務で、Before/After間で責務の分割は起きていない）、OCP・LSP・ISP（継承・拡張の軸がそもそも登場しないシナリオのため、こじつけ感が出る）。

## Java 標準ライブラリ実例の当てはまり直し（chapter01〜11の追加候補）

chapter12（Decorator）以降で標準搭載している「【深堀りN】Java 標準ライブラリにおける〇〇パターンの例」を、chapter01〜11 にも遡って当てはめられないか調査した。候補は必ず実際に OpenJDK のソース（`curl` で現在の master ブランチから取得）を読んでから選定しており、記憶だけで「たぶんこれだろう」というクラス名を書いていない。逆に、最初に思いついた候補（`java.awt.Toolkit` の `createButton` 系メソッド、`java.awt.Component` の `peer` フィールドまわり）はソースを確認した結果、現行 JDK ではすでに削除されていたり、`synchronized(getTreeLock())` や `LightweightPeer` 分岐が絡んで説明コストが高すぎたりしたため、確認した上で候補から外している。

以下、章ごとに「採用candidateあり」の分だけ記載する。まだ深堀りの文章そのものは書いておらず、あくまで「どのクラス・メソッドを引用するか」「どうマッピングするか」のメモ。

### chapter02（Adapter）

**候補：`java.util.Collections#enumeration(Collection<T>)`**

> 引用元: OpenJDK [Collections.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/util/Collections.java)（該当メソッドは現行 master で 5828 行目付近）

```java
        private final Iterator<T> i = c.iterator();

            return i.hasNext();
        }

        public T nextElement() {
            return i.next();
        }
    };
}
```

`Enumeration`（`hasMoreElements`/`nextElement`）が本記事の `PaymentProcessor`（ターゲットのインタフェース）に、`Iterator`（`hasNext`/`next`）が `SamplePayClient`（アダプティ＝適合される側の既存クラス）に、この無名クラスが `SamplePayAdapter`（アダプタ）にそれぞれ対応する。`hasMoreElements` が `i.hasNext()` に、`nextElement` が `i.next()` に処理を委ねているだけの構造は、本記事の `pay` メソッドが `samplePayClient.charge(amount)` に委譲している構造と同型。しかも無名クラスによる**委譲**ベースの実装であり、本記事が「基本的には委譲を使う方が良い」と結論づけている方針とも一致する。ちなみに chapter02 は現状 OpenJDK からの引用が 1 つもないため、この深堀りが追加されれば章内で初の JDK 実例引用になる。

### chapter03（Template Method）

**候補：`java.io.InputStream#read(byte[], int, int)`（`read()` 呼び出しの反復）**

> 引用元: OpenJDK [InputStream.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/io/InputStream.java)（`read()` は 182 行目付近の抽象メソッド、`read(byte[], int, int)` は 283 行目付近）

```java
public abstract int read() throws IOException;
```

```java
public int read(byte[] b, int off, int len) throws IOException {
    Objects.checkFromIndexSize(off, len, b.length);
    if (len == 0) {
        return 0;
    }

    int c = read();
    if (c == -1) {
        return -1;
    }
    b[off] = (byte)c;

    int i = 1;
    try {
        for (; i < len ; i++) {
            c = read();
            if (c == -1) {
                break;
            }
            b[off + i] = (byte)c;
        }
    } catch (IOException ee) {
    }
    return i;
}
```

`InputStream`（抽象クラス）が本記事の `NotificationSender` に、`read()`（抽象メソッド、`FileInputStream` などのサブクラスが実装必須）が `validate`・`buildMessage` などの抽象メソッドに、`read(byte[], int, int)`（1 バイトずつ読む `read()` を繰り返し呼び出して配列を埋める骨組み）が `send` メソッド（テンプレートメソッド）にそれぞれ対応する。ソース中の Javadoc の `@implSpec` にも「`read()` を繰り返し呼ぶだけ」と明記されており、まさに骨組み固定・中身委譲という Template Method の説明そのもの。ただし JDK の `read(byte[], int, int)` には `final` が付いていない点は本記事の `send`（`final`）と異なるので、深堀り本文にする際は「JDK は意図的にオーバーライド差し替えの余地を残している」という一言を添えるとよい。

### chapter06（Prototype）

**候補：`java.util.ArrayList#clone()`（`super.clone()` 後に可変フィールドだけ深いコピーする実例）**

> 引用元: OpenJDK [ArrayList.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/util/ArrayList.java)（343〜353 行目付近）

```java
public Object clone() {
    try {
        ArrayList<?> v = (ArrayList<?>) super.clone();
        v.elementData = Arrays.copyOf(elementData, size);
        v.modCount = 0;
        return v;
    } catch (CloneNotSupportedException e) {
        // this shouldn't happen, since we are Cloneable
        throw new InternalError(e);
    }
}
```

既存の【深堀り①】〜【深堀り②】ですでに `Cloneable.java`・`Object.java` を引用済みだが、これは「マーカーインタフェース」と「`clone` が native で浅いコピーを行う」という*メカニズムそのもの*の説明であり、「実際にどう安全にオーバーライドするか」の実例ではないため非重複。`ArrayList#clone()` は `super.clone()` で浅いコピーをしたあと、可変フィールドである内部配列 `elementData` だけを `Arrays.copyOf` で個別に複製し直しており、これは本記事の深堀り①で紹介した `TaggedNotification#createCopy()`（`super.createCopy()` の後に `tags.clone()` で配列だけ個別コピー）とほぼ同じ手順。JDK 自身が「浅いコピーのままだと危険な可変フィールドだけ深いコピーに昇格させる」という本記事の実務パターンを採用している証拠として使える。

### chapter09（Bridge）

**候補：`javax.swing.JComponent`（`ui` フィールドと `paintComponent` の委譲）**

> 引用元: OpenJDK [JComponent.java](https://github.com/openjdk/jdk/blob/master/src/java.desktop/share/classes/javax/swing/JComponent.java)（`ui` フィールドは 280 行目付近、`paintComponent` は 836〜846 行目付近）

```java
protected void paintComponent(Graphics g) {

        Graphics scratchGraphics = (g == null) ? null : g.create();

        }
```

### chapter11（Composite）

**候補：`java.awt.Container`（`Component` を継承し `List<Component>` を保持）**

`Component` が本記事の `TaskComponent`（共通の抽象型）に、`Container`（複合要素）が `TaskGroup` に、個別の部品（`JButton` など）が `Task` にそれぞれ対応する。`Container` は `Component` を継承しているため、コンテナ自身も 1 つの `Component` として扱え（`JPanel` の中に別の `JPanel` を入れ子にできるのはこのため）、子要素を `Component` 型の `List<Component>` として保持している点も、本記事の `TaskGroup` が `children` フィールドを `List<TaskComponent>` として持つ構造とそのまま一致する。`add(Component comp)` に葉（`JButton` など）も複合（`JPanel` など）もどちらも渡せる点が、本記事の `add(TaskComponent child)` とまったく同じ「個別要素と複合要素の同一視」を体現している。GoF 原典でもウィンドウシステムを例に頻繁に説明される、Composite パターンの代表的な JDK 実例。

### 見送った章

- **chapter01（Iterator）**：すでに `Iterable.java`・`Iterator.java`・`ArrayList.java` を引用済みで、しかもこれらは Iterator パターンの核となる JDK インタフェースそのもの。本文が実質的にすでに「JDK 実例」を解説している状態のため、追加の深堀りは不要と判断。
- **chapter04（Factory Method）**：既存の【深堀り③】（`Arrays.asList` を使った static Factory Method との対比）・【深堀り④】（`StringBuilder`/`String.valueOf` の `toString` 呼び出しチェーン）ですでに JDK ソースを引用済み。これとは別に、「抽象クラス（創出者）が持つ抽象メソッドをサブクラスがオーバーライドして具体的な生成物を決める」という本記事と同じ構造の純粋な Factory Method の実例を `java.base` 内で探したが、JDK の多くは static factory method（またはロケール・設定に応じた内部分岐）を採用しており、本記事の `Factory`/`Management` のように「サブクラスが `createXxx` を素直にオーバーライドする」形の、verifiable でクリーンな例が見つからなかった。無理に探さず見送り。
